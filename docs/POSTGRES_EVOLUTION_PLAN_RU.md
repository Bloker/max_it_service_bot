# План Развития Бота На PostgreSQL (RU)

## 1. Цель
Перейти от "рабочего MVP" к устойчивой production-системе:
- надежная обработка обращений;
- прозрачная работа ролей и прав;
- масштабирование без потери стабильности;
- готовность к интеграциям (мониторинг, CMDB, AD, BI).

## 2. Текущее состояние (после перехода на PostgreSQL)
- Бэкенд заявок и доступов уже работает на PostgreSQL.
- Есть нормализованные схемы: `auth`, `helpdesk`, `integration`, `network`, `ops`.
- Реализованы роли (`user`, `IT specialist`, `admin`), заявки, базовые статусы и workflow.
- Есть задел под историю (`helpdesk.ticket_events`) и комментарии (`helpdesk.ticket_comments`), но потенциал пока не раскрыт полностью.

## 3. Приоритеты развития
1. Стабильность и управляемость.
2. Улучшение UX для пользователей и администраторов.
3. Наблюдаемость и контроль качества.
4. Интеграции с корпоративными сервисами.
5. Автоматизация и интеллектуальные функции.

## 4. Функционал, который стоит реализовать

## 4.1 Для пользователей
- SLA-статус в карточке обращения: "принято", "в работе", "ожидает", "закрыто".
- Оценка после закрытия заявки (1-5 + короткий комментарий).
- Возможность "переоткрыть" закрытую заявку в течение N часов.
- Единый мастер создания заявки:
  - выбор категории;
  - ввод описания;
  - вложения;
  - подтверждение перед отправкой.
- Шаблоны частых проблем (Wi-Fi, ТВ, принтер, VPN) с сокращением времени на ввод.

## 4.2 Для специалистов IT
- Очередь "мои/общие" заявки с фильтрами:
  - категория;
  - отель;
  - статус;
  - просроченные SLA.
- Быстрые действия в один клик:
  - "взять";
  - "передать";
  - "закрыть";
  - "запросить уточнение".
- Внутренние заметки по заявке (не видны пользователю).
- История действий по заявке (кто/когда сменил статус, добавил комментарий).

## 4.3 Для администраторов
- Полноценная админ-панель в чате:
  - список пользователей;
  - роли;
  - привязка к отелям;
  - блокировка/разблокировка;
  - аудит изменений прав.
- Управление справочниками без релиза кода:
  - категории заявок;
  - шаблоны ответов;
  - отели и доступные функции по отелю.
- Гибкая модель доступа:
  - временные роли;
  - замещение;
  - делегирование прав.

## 5. Улучшения архитектуры на PostgreSQL
- Включить полноценное использование `helpdesk.ticket_events` для каждого изменения статуса.
- Разделить пользовательские и служебные комментарии через `ticket_comments.direction`.
- Хранить метаданные вложений в `helpdesk.ticket_attachments` и не терять связь с тикетом.
- Добавить soft-delete для пользователей и бизнес-сущностей (где нужно), чтобы не терять историю.
- Добавить версионирование справочников (категории, роли, фичи отелей).
- Добавить контроль целостности:
  - ограничение переходов статусов;
  - валидные SLA-сроки;
  - защита от "гонок" через транзакции и блокировки только нужных строк.

## 6. Сервисы для подключения и усиления бота

## 6.1 Рекомендуется подключить в первую очередь
- Redis:
  - сессии и state-машины диалогов;
  - таймеры автосборки сообщения;
  - rate-limit и антиспам.
- S3/MinIO:
  - хранение вложений (фото/файлы);
  - разгрузка чатов и БД.
- Prometheus + Grafana:
  - метрики по заявкам, SLA, ошибкам, времени ответа.
- Sentry:
  - централизованный сбор исключений и трассировок.

## 6.2 Корпоративные интеграции (по готовности)
- LDAP/AD:
  - автоподтягивание ФИО/должности/подразделения;
  - единая модель идентификации пользователей.
- CMDB/инвентаризация:
  - привязка заявки к устройству/сервису;
  - сокращение ручного ввода.
- Zabbix/PRTG/другой мониторинг:
  - автоматическое создание заявок по алертам.
- BI (Metabase/Power BI):
  - отчеты по нагрузке, категориям, SLA, качеству обслуживания.

## 6.3 Продвинутый уровень (после стабилизации)
- Очередь задач (RabbitMQ/Kafka):
  - надежные фоновые процессы;
  - повторные доставки уведомлений;
  - отложенные операции.
- AI/LLM-сервис:
  - автоклассификация текста заявки;
  - предложение шаблона решения;
  - краткое резюме длинной переписки.

## 7. Roadmap внедрения

## Этап 1 (1-2 недели): "Стабильный фундамент"
- Аудит событий в `ticket_events`.
- Технические метрики и алерты.
- Логи с correlation/request id.
- Redis для state и таймеров.

## Этап 2 (2-4 недели): "Сильный helpdesk workflow"
- Комментарии и внутренняя заметка специалиста.
- Вложения через S3/MinIO + метаданные в Postgres.
- SLA-модель: срок реакции, срок решения, просрочка.
- Отчеты для админов по открытым/просроченным заявкам.

## Этап 3 (3-6 недель): "Админ и масштабирование"
- Расширенное управление пользователями и ролями в интерфейсе бота.
- Справочники категорий/шаблонов без изменения кода.
- Интеграция с LDAP/AD (если доступно).
- Базовая BI-аналитика.

## Этап 4 (дальше): "Автоматизация и AI"
- Интеграция с мониторингом для автосоздания инцидентов.
- Автоклассификация и рекомендации оператору.
- Проактивные уведомления по повторяющимся сбоям.

## 8. KPI для контроля развития
- Среднее время до взятия заявки в работу.
- Среднее время до решения.
- Доля заявок, закрытых в SLA.
- Доля повторных обращений по той же проблеме.
- Удовлетворенность пользователя после закрытия заявки.
- Количество ошибок/падений на 1000 апдейтов.

## 9. Что можно начать прямо сейчас (быстрые улучшения)
1. Добавить `ticket_events` на все операции по заявке.
2. Добавить оценку после закрытия заявки.
3. Добавить фильтр "просроченные" для админов и специалистов.
4. Подключить Sentry и базовые метрики.
5. Вынести runtime-state диалогов в Redis.

## 10. Риски и как их снизить
- Риск: усложнение логики ролей и доступов.
  - Мера: единая точка проверок в `access_service`, тест-кейсы на права.
- Риск: рост количества интеграций и точек отказа.
  - Мера: staged rollout, feature flags, fallback-режимы.
- Риск: деградация UX при добавлении новых шагов.
  - Мера: короткие сценарии, кнопки вместо ручного ввода, A/B проверка текстов.

## 11. Итого
Основа на PostgreSQL уже позволяет строить зрелый service desk.
Оптимальный путь: сначала наблюдаемость и стабильность, затем SLA/вложения/админ-функции, после этого корпоративные интеграции и автоматизация.
