# Manual Checklist (RU)

## A. Регистрация/доступ
1. Пользователь запускает `/start` и видит меню.
2. Пользователь без IT/Admin роли не получает доступ к network tools.
3. IT-специалист видит сетевое меню и может запускать инструменты.

## A1. Пользовательское inline-меню
1. Обычный пользователь пишет `/start`.
2. Пользователь видит компактное меню `Меню IT Help Desk`.
3. Первая кнопка в меню — `Создать обращение`.
4. Обычный пользователь не видит `Сетевые инструменты`.
5. Обычный пользователь не видит `Права администратора`.
6. Нажатие `Создать обращение` открывает выбор категории.
7. В выборе категории есть кнопка `Главное меню`.
8. После отмены создания обращения пользователь возвращается в главное меню.
9. После успешной отправки заявки пользователь получает отдельное сообщение `Заявка принята...`.
10. После подтверждения отправки пользователь снова видит главное меню.
11. `Мои обращения`, `Помощь` и `О боте` возвращают пользователя к меню с кнопкой `Создать обращение`.
12. IT specialist видит `Сетевые инструменты`.
13. Admin видит `Права администратора`.

## A2. Jamaica room-ticket flow
1. Пользователь Jamaica открывает `/menu`.
2. Видит меню: `Заявка по номеру`, `Прочее`, `Мои заявки`, `Помощь`.
3. Если для отеля включен `wifi_guest_issue`, под `Прочее` есть кнопка `Проблема Wi-Fi у гостя`.
4. Нажимает `Заявка по номеру` и получает prompt с единственной кнопкой `Отмена`.
5. Вводит существующий номер `112` и получает только список категорий: `ТВ`, `Телефония`, `Интернет`, `Замок`, `Прочее`.
6. Кнопок `Главное меню`, корпусов и домиков на шаге выбора категории нет.
7. После выбора категории бот просит описание и показывает только кнопку `Отмена`.
8. `Отмена` на промежуточном шаге сбрасывает draft и возвращает в главное меню.
9. Неизвестный номер показывает `Такого номера не существует` и кнопки `Ввести заново`, `Создать как Прочее`, `Главное меню`.
10. `Создать как Прочее` продолжает создание заявки без `location_id`.
11. В групповой карточке Jamaica room-ticket показывается `Объект: Номер 112 (ТВ)` или `Объект: Домик 15 (Интернет)`.
12. В Jamaica room-ticket карточке не должно быть отдельной строки `Категория` и нижнего блока `Объект / Категория объекта`.
13. Телефон в карточке выводится отдельной строкой `Тел: ...`.
14. Для Jamaica room-ticket с номером в групповой карточке есть кнопка `История номера`.
15. Для Jamaica `Прочее` без номера кнопки `История номера` нет.
16. Нажатие `История номера` отправляет отдельное сообщение в группу, а не заменяет основную карточку.
17. В истории выводятся только ticket id, категория, статус и дата без телефона, имени пользователя и описания.
18. Текущая заявка не попадает в собственную историю.

## B. Создание и маршрутизация заявки
1. Авторизованный пользователь создаёт заявку по шагам (категория -> текст -> подтверждение).
2. Заявка появляется в групповом чате специалистов.
3. Пользователь видит заявку в `/my`.
4. Пользователь создаёт заявку с фото: фото остаётся в attachments карточки.
5. Пользователь создаёт заявку с видео/файлом: вложение доходит в группу без ошибки отправки.
6. Пользователь создаёт заявку с audio/voice: карточка появляется в группе, а audio/voice приходит отдельным нативно пересланным сообщением MAX.
7. Если audio/voice отправлено вместе с текстом, native forward должен сохранить исходный текст сообщения.
8. Если пользователь отправил только audio/voice без текста, заявка всё равно должна отправиться через 20 секунд; в описании карточки допустима заглушка `[аудиосообщение]`.
9. В группе не должны появляться приватные media URL или token.
10. В логах по audio/voice должны быть события `Audio detected`, `Audio native forward started`, затем `Audio message forwarded natively` или controlled fallback.

## C. Работа специалиста по заявке
1. Специалист берёт заявку в работу (кнопка или `/take T-xxxxx`).
2. Статус меняется и карточка заявки обновляется.
3. Специалист может `/release`, `/clarify`, `/close` в рамках прав.
4. Команда `/open` показывает список открытых заявок.

## C1. Уточнение по заявке
1. В группе специалистов нажать `Запросить уточнение`.
2. Проверить, что бот прислал prompt без текста `/cancel` и с inline-кнопкой `Отмена`.
3. Нажать `Отмена` тем же специалистом: prompt должен удалиться, статус заявки не меняется.
4. Повторить `Запросить уточнение` и отправить текст вопроса обычным сообщением.
5. Пользователь должен получить вопрос в личном чате с кнопкой `Ответить`.
6. Основная карточка заявки должна обновиться на месте, статус стать `ожидает пользователя`.
7. В карточке должен появиться блок `Последнее уточнение`.
8. Prompt и сообщение специалиста с вопросом должны удалиться из группы.
9. Отдельное сообщение `Уточнение отправлено...` в группе появляться не должно.
10. Другой специалист не должен иметь возможность отменить чужое уточнение.
11. Пользователь нажимает `Ответить`, затем вводит текст или вложение.
12. Ответ должен прийти в группу специалистов по нужной заявке с кнопкой `Прикрепить к карточке`.
13. Нажать `Прикрепить к карточке`: ответ должен появиться в основной карточке заявки.
14. Если исходная заявка была с фото, это фото должно остаться в карточке после прикрепления ответа.
15. Если уточнение специалиста было с фото, это фото должно остаться в карточке после прикрепления ответа.
16. Если пользователь отправлял фото/видео/файл, вложения должны добавиться в карточку вместе с кнопками заявки.
17. Audio/voice в уточнениях и ответах на уточнение должно идти через native forward, а не как обычный attachment карточки.
18. Специалист отправляет audio/voice как вопрос уточнения: пользователь должен получить текст уточнения с кнопкой `Ответить`, а audio/voice отдельным нативным сообщением MAX.
19. Пользователь отвечает audio/voice через кнопку `Ответить`: в группе должен появиться текстовый блок ответа с кнопкой `Прикрепить к карточке`, а audio/voice отдельным нативным сообщением MAX.
20. Пользователь отвечает audio/voice через reply на сообщение уточнения: поведение должно быть таким же, как через кнопку.
21. В карточке после прикрепления audio-only ответа допустим текст `[аудиосообщение]`; приватные media URL/token не должны появляться.
22. В логах по media-сообщению должна появиться строка `Message attachments filtered` без token/url значений.
23. После прикрепления ответа статус должен вернуться в `в работе`, а кнопки должны соответствовать этому статусу.
24. Отдельное сообщение ответа пользователя в группе должно удалиться.
25. Если пользователь делает reply на сообщение уточнения без кнопки, старый сценарий тоже должен работать.
26. После применения миграции `20260702_persist_ticket_comments_attachments.sql` на test DB создать заявку с фото, отправить уточнение с фото и прикрепить ответ пользователя с фото/файлом.
27. Перезапустить тестового бота и выполнить действие по этой заявке, которое обновляет карточку: блоки `Последнее уточнение` и `Ответ пользователя` должны сохраниться.
28. После рестарта карточка должна восстановить вложения, у которых был reusable token; приватные URL/token не должны отображаться в тексте и логах.
29. Если PostgreSQL-контекст недоступен, сценарий уточнения должен продолжать работать runtime-only, а в логах должен быть warning без падения бота.

## D. Reply-логика
1. Команда специалиста в reply к карточке заявки корректно определяет ticket id.
2. Статус обновляется для нужной заявки, соседние заявки не затрагиваются.

## D1. Закрытие заявки с ответом пользователю
1. Создать тестовую заявку от пользователя с телефоном в формате `8XXXXXXXXXX`.
2. Проверить в групповой карточке, что телефон отображается как `+7XXXXXXXXXX`.
3. В MAX web проверить, стал ли телефон кликабельным через HTML `tel:` или удобнее для копирования.
4. Проверить, что карточка без телефона показывает `тел.: не указан` и не содержит пустой ссылки.
5. Взять заявку в работу.
6. Проверить кнопки карточки: `Освободить`, `Закрыть`, `Закрыть с ответом`, `Запросить уточнение`, `Не закрытые заявки`.
7. Нажать `Закрыть с ответом`.
8. Проверить prompt `Введите сообщение пользователю о выполненной работе.` с кнопкой `Отмена`.
9. Нажать `Отмена` тем же специалистом: prompt должен удалиться, статус заявки не меняется.
10. Повторить `Закрыть с ответом` и отправить текст ответа специалиста.
11. Пользователь должен получить сообщение `Заявка T-xxxxx выполнена.`, блок `Ответ специалиста` и кнопку `Главное меню`.
12. Карточка в группе должна обновиться на месте: статус `закрыто`, кнопка только `Не закрытые заявки`.
13. В карточке должен появиться блок `Ответ при закрытии`.
14. Prompt и сообщение специалиста с ответом должны удалиться из группы.
15. Другой специалист не должен отменять чужую сессию закрытия с ответом.
16. Если отправка пользователю не удалась, заявка не должна закрываться, а сессия должна остаться активной.

## E. Пользовательский фидбек
1. Пользователь получает подтверждение после отправки заявки.
2. Пользователь видит корректные статусы в списке своих заявок.

## F. Network tools и corporate policy
1. Разрешённый внутренний target проходит проверку и выполняется.
2. Внешний/запрещённый target отклоняется политикой.
3. Отключённый feature flag возвращает ожидаемое сообщение «инструмент отключен».
4. Ошибки системных утилит (нет binary/timeout) отображаются контролируемо.

## G. Логи и устойчивость
1. В логах видны ключевые события: создание заявки, смена статуса, отказ policy, ошибки network tools.
2. Бот продолжает работу после неуспешных диагностических команд.

## G1. Webhook mode
1. В dev/test окружении выставить `MAX_UPDATE_MODE=webhook`.
2. Проверить, что backend слушает только внутренний адрес `127.0.0.1:8080`.
3. `GET /health` возвращает `200` и не содержит token/secret/DB password.
4. `POST /max-webhook` без `X-Max-Bot-Api-Secret` при заданном secret возвращает `403`.
5. `POST /max-webhook` с неверным secret возвращает `403`.
6. `POST /max-webhook` с корректным secret и валидным JSON возвращает `200`.
7. Невалидный JSON возвращает `400`.
8. В логах webhook нет raw payload, token, password, private media URL.
9. Long Polling и webhook subscription одновременно не использовать.
10. Перед production switch Nginx `/max-webhook` должен быть переключен с `503` на `proxy_pass http://127.0.0.1:8080/max-webhook`.

## H. Audit/events/observability
1. На test DB применена миграция `20260702_audit_events_observability.sql`.
2. Создать новую заявку и проверить `helpdesk.ticket_events.event_type = ticket_created`.
3. Проверить, что после отправки карточки в группу есть `message_relayed_to_group`.
4. Если заявка была с фото/файлом, проверить `attachment_received`.
5. Специалист нажимает `Взять в работу`: проверить `ticket_assigned` и `ticket_status_changed`.
6. Специалист нажимает `Запросить уточнение`: проверить `ticket_waiting_user` и `clarification_sent_to_user`.
7. Пользователь отвечает: проверить `user_reply_received` и `message_relayed_to_group`.
8. Специалист нажимает `Прикрепить к карточке`: проверить `user_reply_attached_to_card`.
9. Обновление карточки должно дать `ticket_card_updated`; при контролируемом сбое должно быть `ticket_card_update_failed`.
10. Специалист закрывает заявку: проверить `ticket_closed` и `ticket_status_changed`.
11. Пользователь подаёт заявку на доступ: проверить `ops.audit_log.action = access_requested`.
12. Admin одобряет/отклоняет доступ: проверить `access_approved` или `access_rejected`.
13. Обычный пользователь пытается выполнить запрещённое действие: проверить `access_denied`.
14. IT/admin запускает разрешённый network tool: проверить `network.tool_runs.status = success`.
15. IT/admin запускает запрещённый внешний target: проверить `network.tool_runs.status = denied` и audit `network_tool_denied_by_policy`.
16. Проверить, что в `payload`, `metadata`, `output_excerpt` нет token, password, api_key и приватных media URL.

## I. SQLAlchemy foundation
1. Проверить, что текущий backend заявок по-прежнему `postgres` через существующие psycopg repositories.
2. Убедиться, что SQLAlchemy foundation не вызывает `metadata.create_all()` и не применяет DDL при старте бота.
3. Для будущих SQLAlchemy repository-проверок использовать только `test_dev_max`, пока нет отдельного решения о production rollout.
4. Запустить `.venv/bin/python -m unittest tests.test_sqlalchemy_foundation -v`.

## J. Normalized ticket source of truth
1. Убедиться, что default `MAX_TICKET_SCHEMA_MODE=legacy`.
2. Запустить read-only сверку: `MAX_TICKET_BACKEND=postgres .venv/bin/python scripts/reconcile_ticket_schemas.py --db test_dev_max`.
3. Проверить, что `pending_legacy=0`, `pending_normalized=0`, `only_public=0`, `only_helpdesk=0`.
4. В test/dev окружении выставить `MAX_TICKET_SCHEMA_MODE=shadow_read` и проверить создание/взятие/закрытие заявки; warning-логи shadow mismatch должны отсутствовать при синхронизированных данных.
5. В test/dev окружении выставить `MAX_TICKET_SCHEMA_MODE=normalized` и проверить полный lifecycle заявки.
6. Проверить, что новая заявка в normalized mode появляется в `helpdesk.tickets` без `PENDING`.
7. Проверить, что comments/events/attachments и `integration.message_links` продолжают ссылаться на `helpdesk.tickets.id`.
8. Для rollback вернуть `MAX_TICKET_SCHEMA_MODE=legacy` и перезапустить только dev/test bot.
9. Production не переключать на `shadow_read` или `normalized` без отдельной команды владельца.

## K. Simplified Knowledge Base MVP (Stage 4.3)
1. Под IT/admin открыть `База знаний` -> `Джамайка` -> `ТВ`.
2. Проверить, что темы отображаются кнопками без цифр, source или status.
3. Открыть тему: в карточке должны быть только путь, тема и текст; строк `Источник`, `Объект`, `Статус`, `candidate`, `active`, `internal` быть не должно.
4. Открыть пустую категорию: сообщение должно содержать `Тем пока нет.`.
5. Через `Добавить запись` создать тему и заметку в `Джамайка` -> `ТВ`; новая тема должна появиться в списке.
6. В Jamaica-заявке нажать `Комментарий`, ввести текст; карточка заявки обновляется на месте, а блок `Внутренний комментарий` не содержит служебных полей.
7. В БД `test_dev_max` проверить `ticket_comments.direction=internal_comment`, `meta.visible_to_user=false`, `meta.added_to_knowledge_base=false`, а также `meta.location_id` для номера.
8. Убедиться, что внутренний комментарий не создал тему в `knowledge_articles`.
9. Проверить, что обычный пользователь не видит `База знаний`, а IT/admin видит.
10. Повторить `Запросить уточнение`, `История номера` и `Закрыть с ответом`.

## L. Internal Comments (Stage 4.4)

2. Нажать `Комментарий`. Prompt должен сообщать, что текст не отправится пользователю и не попадёт в БЗ.

4. Проверить, что пользователю ничего не пришло и новая тема БЗ не появилась.
5. Для обычного закрытия и закрытия с ответом пользователь должен получить кнопку `Главное меню`.

## M. Media MVP (Stage 4.7, test-only)
1. В `test_dev_max` открыть активную Jamaica-заявку и нажать `Комментарий`.
2. Убедиться, что тема не запрашивается; prompt сообщает о 15 секундах тишины.
3. Отправить текст, затем фото/видео/файл. После 15 секунд проверить один
   `internal_comment`, обновление карточки и отсутствие сообщения пользователю.
4. Убедиться, что внутренняя запись не появилась в БЗ.
5. Через `База знаний -> Добавить запись` создать тему, текст и фото/видео/файл;
   убедиться, что статья и счётчики вложений доступны IT/admin.
6. Audio/voice в этом MVP должны быть отклонены контролируемым сообщением;
   они не сохраняются в `helpdesk.media_attachments`.
7. Нажать `Закрыть с ответом`, отправить текст и при необходимости фото/видео/файл;
   через 15 секунд пользователь должен получить ответ и кнопку `Главное меню`.
8. Проверить, что временные prompt и сообщения специалиста удаляются best-effort,
   а основная карточка заявки сохраняется.
9. Проверить, что фото и видео из закрытия с ответом отображаются также на
   закрытой карточке заявки в групповом чате, до её inline-клавиатуры.
10. Нажать у пользователя `Главное меню`: должно открыться Jamaica-меню с
    кнопками `Заявка по номеру`, `Прочее`, `Мои заявки`, `Помощь` и, когда
    включена функция, `Проблема Wi-Fi у гостя`.

## N. Stage 4.8 Production Rollout
1. До отдельного разрешения владельца не выполнять production writes, candidate DB,
   backup, migration, deploy или restart `max-it-bot.service`.
2. Использовать только `scripts/seed_jamaica_production_catalog.py` с явным
   `--allow-production`; `seed_jamaica_knowledge_base_test_data.py` в production
   не запускать.
3. Перед rollout применить production migrations и production-safe seed сначала
   к candidate DB из свежего backup production.
4. В candidate DB проверить: 253 Jamaica locations, 5 категорий, 4 knowledge scopes,
   `knowledge_articles=0`, KB media `=0`, reconciliation без расхождений.
5. После отдельного разрешения проверить production KB перед migration. Если в ней
   уже есть реальные статьи или KB media, остановиться и показать результат владельцу.
