# AGENTS.md

## Проект
- Внутренний VK MAX IT Help Desk bot.
- Основные блоки: `helpdesk` (заявки), `network` (диагностика), `admin` (роли/доступ), `bot/handlers` (точки входа), `config` (env + runtime config).

## Что важно не ломать
- Роли: `user`, `IT specialist`, `admin`.
- Централизованные проверки доступа в `app/admin/services/access_service.py`.
- Границы `handler -> service -> repository`.
- Ограничения corporate policy для network tools (домены/подсети/hosts/device types).
- Минимальную модель тикета этапа 4 без лишней ITSM-сложности.

## Правила изменений
- Не хардкодить токены, chat_id, роли, policy и feature-флаги: только через `config/config.py` и env.
- Не вносить data-access логику в handlers.
- Новые сценарии по заявкам добавлять через `TicketLifecycleService` и репозитории.
- Если нужна новая проверка прав: сначала в `access_service`, потом подключение в handlers/services.
- Для network блока сначала policy/validation, потом выполнение команды.

## Ответственность модулей
- `app/bot/handlers/*`: orchestration пользовательских и служебных сценариев.
- `app/helpdesk/*`: бизнес-логика заявок, состояния, тексты/клавиатуры.
- `app/network/*`: сетевые инструменты, адаптеры, policy, тексты/клавиатуры.
- `app/admin/services/*`: role/access checks.
- `config/*`: конфигурация и логирование.

## Работа с конфигом
- Все новые настройки документировать в `config/.env.example` и корневом `.env.example`.
- Значения по умолчанию должны быть безопасными.
- Валидация формата и диапазонов — в `get_config()`.

## Работа с ролями и доступом
- `user`: пользовательское меню и создание/просмотр своих заявок.
- `IT specialist`: работа с заявками и network tools.
- `admin`: полный доступ, включая админ-действия и override ограничений по заявкам.

## Работа с network tools
- Проверка target обязательно проходит через `target_validator` и `CorporateTargetPolicy`.
- Любой denied по policy должен логироваться.
- Ошибки запуска/timeout утилит должны возвращаться пользователю в контролируемом виде.

## Проверки перед итогом
- Синтаксис Python (рекомендуется AST/compile check по проекту).
- `python -m unittest discover -s tests -v`.
- Ручной smoke по сценарию helpdesk + network (см. `docs/MANUAL_CHECKLIST_RU.md`).

## Рефакторинг принципы
- Малые шаги, без переписывания проекта с нуля.
- Сохранять совместимость текущих сценариев этапов 1–4.
- Убирать дубли и технический мусор только если это не ломает UX и архитектурные границы.

## Формат итогового отчета изменений
- Что изменено и зачем.
- Какие проверки запущены и их результат.
- Что не покрыто (честно, без замалчивания).
- Рекомендованный backlog следующего этапа.
